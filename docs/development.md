# Provider implementation

`src/provider.js` implements the independent provider contract from `dot-bridge-core`. Shared authentication, MCP, callback validation, encrypted state and final-reply lifecycle remain in core.

The implementation independently uses the documented upstream wire fields: `getupdates`, `getuploadurl`, `sendmessage`, token headers, `get_updates_buf` and per-message `context_token`. It does not copy either framework or load their configuration. `bot_agent` identifies DotBridge. No login helper, typing-status or proactive-send API is included.

Only complete user messages from the configured private owner are accepted. Bot/unfinished/group events are filtered; a present recipient must match the configured bot. Message IDs and sequence numbers are parsed from JSON source text before Number rounding can occur. A stable hashed composite ID is passed to core, which owns durable deduplication. Polling cursor persistence follows successful awaited ingestion of the entire batch. HTTP 401/403 or iLink session error -14 stops polling pending operator login.

Each final reply makes one `sendmessage` POST to the original private peer, carrying the original stored context and a stable hashed `client_id`. This field is not treated as a server-side exactly-once guarantee. No mutation is automatically retried. A 3800-character text bound and a zero-character media-caption limit avoid partial multi-message reply delivery. API responses are capped at 2 MiB; requests reject redirects and retain the HTTPS hostname's normal TLS checks.

`readAttachment({message,attachmentIndex})` returns up to 8 MiB of bytes from the authenticated message's private `replyContext.mediaRefs` array. It rechecks owner, conversation, index, public kind and the fixed official CDN origin/path. Keys support image hex, base64 of 16 raw bytes and base64 of 32 hex characters. AES-128-ECB with PKCS7 is the official wire format, not a new general encryption design. File length/MD5 are checked when supplied; invalid keys, lengths, padding and destinations fail closed. Incoming invalid references retain their public metadata without saving unsafe URLs or making requests. Total private metadata is bounded so a bad attachment cannot stall the polling cursor. Audio MIME is identified from bytes; SILK uses the shared core `audio/silk.js` worker with pinned `silk-wasm@3.7.1` to produce WAV, with a 10-second worker deadline, 120-second audio bound and runtime cancellation. Transcription remains in core. No transient audio files or duplicate decoder implementation are created.

`validateMediaReply` is synchronous and runs before queuing and again before sending. Image/file uploads use bounded in-memory bytes, a temporary per-upload AES key, `getuploadurl`, and one CDN POST; the bot Bearer token is never sent to the CDN. Full URLs must match `https://novac2c.cdn.weixin.qq.com/c2c/upload`; invalid server-provided URLs do not fall back to a second target. Core's synchronous `authorize()` guard is checked before upload setup, CDN upload and final message send, so expiry or revocation during an upload blocks the next mutation. An accidentally async guard is rejected, not ignored. Upload and final-send errors never retry. Image captions, voice-bubble sending, arbitrary URL inputs and video binary handling are deliberately not advertised. Keys are ephemeral protocol material and are not persisted as new account credentials.

Synthetic tests cover delayed/failed ingestion, cursor survival, uint64 identity, owner/account/group filtering, metadata and transcript mapping, all supported media reads, AES key encodings, size/digest/padding limits, upload encryption, hostile URL refusal, safe reply routing, no retry on uncertain sends and stop cancellation. They do not verify a real iLink account or a real dot subscription. Run `npm run check` and `npm test` with Node 24.15 or later in the 24.x line. Channel media tools require the matching shared-core release; the pinned vendor artifact is updated centrally during coordinated packaging.
